## Behavior and integration

The data shape is the existing `TaskRow.task.strict` Boolean. No new state, schema, public operation, or policy implementation is needed. `TaskMenuItems` adds **Make strict (one-way)**. Its help and accessibility hint explain that it prevents new unblock requests and preserves existing unblocks until expiry. Strict tasks show a disabled **Strict (one-way)** menu item and a quiet **Strict** label beside the category.

The action calls `model.perform { try model.store.setTaskStrict(row.id) }`. `AppModel.perform` reloads after success or failure. `reload` refreshes task collections and calls `refreshBlocking`, which reads fresh Store policy and reconciles enforcement. Store writes also post the existing `ChangeSignal` for other processes. No AppModel integration edit is required.

The responsible Store operation checks `editableTask` before its already-strict return. Closed days, deleted plans, and deleted tasks retain their guards. A stale menu choice therefore reports the Store error through the existing `model.error` and `ErrorNote` path. A repeated action on a still-editable strict task is a no-op. There is no loosening action.

An existing exception remains effective until its recorded expiry. New requests fail with `BlockError.strictSession`, including repeat requests for a rule that is already open. Finishing or stopping the session retains task strictness and uses existing timer behavior.

| Before | After | Why |
| --- | --- | --- |
| Existing tasks have no strictness control. | The shared native task menu contains one tightening action. | Today, Inbox, Upcoming, and Done reuse the existing control. |
| A strict task has no visible card state. | The secondary metadata line shows Strict. | Success remains visible after the menu closes and after reload. |
| Category, Block, and Schedule use stable task controls. | The controls retain their existing clock dependencies. | This change adds no clock read, observation, animation, or category-picker change. |
